# RAG Retrieval Lab

**How good is your retrieval? Measure it.**

Most "chat with your documents" projects stop at a demo. This project treats the *retrieval* step of
Retrieval-Augmented Generation (RAG) as something to be **measured**: it builds a small RAG system over a
document collection and runs a controlled experiment comparing

| Dimension | Options compared |
|---|---|
| Chunking strategy | fixed-size windows · sentence packing · heading-aware (Markdown sections) |
| Chunk size | 50 · 100 · 200 words (configurable) |
| Retriever | BM25 (keyword) · dense embeddings · hybrid (Reciprocal Rank Fusion) |
| Embedding model | MiniLM · BGE-small · (offline) LSA baseline |

using **Hit@1/3/5, MRR@10** and a split of **lexical vs paraphrased questions**. A Streamlit app lets you ask
questions interactively and see the retrieved passages; an optional switch generates the final answer with Claude.

> The bundled corpus is a **fictional** university rule book (9 short documents) with 30 hand-written questions, so the
> repo runs out of the box. Swap in your own documents (see [Use your own documents](#use-your-own-documents)) for
> meaningful conclusions.

## Quick start

```bash
git clone <your-repo-url> && cd rag-retrieval-eval
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt

python -m unittest discover -s tests -v                # 17 tests, ~2 s
python -m src.evaluate                                 # runs the experiment grid -> results/
streamlit run app.py                                   # interactive app
```

Useful variants:

```bash
python -m src.evaluate --dense-models minilm,bge-small   # compare two embedding models
python -m src.evaluate --dense-models lsa                # fully offline (no model download)
python -m src.evaluate --dense-models none               # BM25 only
python -m src.evaluate --chunkers fixed --sizes 25,50,100,150,300
```

The first run with `minilm` / `bge-small` downloads the model from Hugging Face (~90 MB / ~130 MB).

## How the evaluation works

1. **Questions** live in `data/eval/questions.csv`: `id, question, evidence, source_doc, qtype`.
2. `evidence` is a short phrase copied verbatim from the document that answers the question.
3. A retrieved chunk is **relevant** if it *contains the evidence phrase* (case/whitespace-insensitive).
   Defining relevance by text instead of chunk IDs is what makes different chunk sizes and strategies comparable.
4. For each question we take the rank of the first relevant chunk and compute
   * **Hit@k** – share of questions with a relevant chunk in the top *k*
   * **MRR@10** – mean of 1/rank of the first relevant chunk (0 if not in top 10)
   * **doc_hit_at_3** – a looser check: did any top-3 chunk come from the correct *document*?
5. `qtype` marks each question as `lexical` (shares key words with the answer) or `paraphrase` (different wording),
   which is where dense retrieval is expected to help.

Outputs written to `results/`: `summary.csv`, `per_question.csv` (every question × configuration),
`mrr_by_config.png`, `hit3_by_question_type.png`.

### Design notes
* **BM25** is implemented from scratch in ~40 lines (`src/retrievers.py`), so there is no hidden dependency.
* **Dense retrieval** uses normalised embeddings and exact cosine search in NumPy. At this scale FAISS adds nothing.
* **Hybrid** uses Reciprocal Rank Fusion, `score = Σ 1/(60 + rank)`, which needs no score calibration.
* **LSA** (TF-IDF + truncated SVD) is a classical, offline "dense" baseline, handy for CI and for showing what
  neural embeddings actually add.
* `heading` chunks at sizes 100 and 200 are identical on the sample corpus because every section is shorter than
  100 words; they only differ on corpora with longer sections.

## Project structure

```
app.py                     Streamlit UI (Ask tab + Evaluation tab)
src/
  loader.py                load .md / .txt / .pdf files
  chunking.py              fixed, sentence and heading chunkers
  retrievers.py            BM25, dense (sentence-transformers / LSA), hybrid RRF
  metrics.py               relevance test, Hit@k, MRR@k
  pipeline.py              builds retrievers for a set of chunks
  evaluate.py              experiment grid, CSV + plots
  generate.py              extractive or Claude-generated answers
data/corpus/               sample documents
data/eval/questions.csv    30 evaluation questions
tests/test_core.py         unit tests, incl. checks that every evidence phrase exists in the corpus
results/                   generated by src.evaluate
```

## Use your own documents

1. Put `.md`, `.txt` or `.pdf` files in a folder, e.g. `data/my_corpus/` (public examples: RBI/SEBI circulars,
   a university handbook, a product manual, your company's HR policy).
2. Write **30+ questions** the way real users would ask them, including some paraphrased ones, and copy a
   short evidence phrase for each from the source text into a new CSV with the same columns.
3. Check the CSV: `python -m unittest discover -s tests` verifies that each evidence phrase exists exactly once
   (adapt the paths in `tests/test_core.py`).
4. Run `python -m src.evaluate --corpus data/my_corpus --questions data/my_questions.csv`.

## Optional: LLM answers

```bash
pip install anthropic
export ANTHROPIC_API_KEY=...        # optional: export ANTHROPIC_MODEL=<model name>
streamlit run app.py                # tick "Generate an answer with Claude"
```

The prompt tells the model to answer only from the retrieved passages, cite them, and say when the answer is
not in the context. Answer quality is *not* part of the automatic evaluation; only retrieval is measured.

## Limitations

* With 30 questions one question is worth 3.3 percentage points, so small gaps between configurations are
  not statistically meaningful. Add more questions or bootstrap confidence intervals before drawing strong conclusions.
* Evidence-containment is strict: tiny chunks can split an evidence phrase across two chunks and be scored as a miss.
  This is a real effect of over-small chunks, but keep evidence phrases short.
* The sample corpus is small and clean, so scores are high and differences are modest.
* Only retrieval is evaluated. Faithfulness and answer correctness of generated text are future work.

## Ideas for extension

Cross-encoder re-ranking · query rewriting · metadata filters · bootstrap confidence intervals ·
LLM-as-judge for answer faithfulness · multilingual (Hindi/Punjabi) questions.
